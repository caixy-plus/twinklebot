# TwinkleBot

Multi-Bot AI desktop & mobile agent: orchestrates Gemini / OpenAI / DeepSeek / Anthropic / Vertex AI models with a local or cloud runtime, OrbStack Ubuntu XFCE sandbox (`:1`, 1440x900), and cross-platform Host Executor bridge.

- **Stack & Build**: Node.js 22.13+, ESM, TypeScript (`tsc`). `tsconfig.json` compiles `src/` (server/agent/store/electron/shared/tests) to `dist-server/`; `tsconfig.web.json` compiles `src/web/` to `public/dist/`; `tsconfig.landing.json` compiles `src/landing/` to `landing/dist/`. Only runtime dependency: `@google/genai` (>= 2.29.1; use the Interactions API only for Gemini, never `generateContent` or legacy `@google/generative-ai`).
- **Architecture**:
  - `src/shared/` holds shared entity types, DTOs, and browser-safe modules (`accounts-store.ts`, `skills-catalog.ts`, `context-compression.ts`).
  - `src/server/` serves `127.0.0.1:3230` (via `dist-server/src/server/index.js`, split into `context.ts`, `http-utils.ts`, `static.ts`, and `routes/*.ts`).
  - `src/agent/` holds the agent loop, smart router, context compression, policy, model adapters (`providers/*.ts`), and bot tools (`bot-tools/*.ts`).
  - `src/store/` owns JSON/NDJSON session, event, history, skill, schedule, and vault persistence under `data/`.
  - `src/web/` (`app.ts`, `modules/*.ts`, `mobile-*.ts`) + `public/` form the Web/Desktop/Mobile UI; `APP_TARGET=mobile node scripts/build-web.mjs` strips backend/Electron files into `dist-web/` for Capacitor (`android/` with native `LanDiscoveryPlugin`, `ios/`).
  - `src/electron/` + `electron/preload.cjs` package the Electron app; `executor/executor.py` runs inside Ubuntu (Python 3 stdlib only, `twinklebot-executor.service`, port `7300`, bearer token).
- **Commands**: `npm run typecheck`, `npm run build:ts`, `npm run build:ota`, `npm test` (builds TS then runs `node --test`), `npm run electron:pack:mac` / `electron:dist`, `npm run mobile:build:web` / `mobile:apk:debug`, and `orb -m ubuntu python3 -m unittest discover -s executor -v`. For automated UI/E2E testing, prefer `http://127.0.0.1:3230` directly.
- **Versioning & GitHub Releases (`v1.0.0` Baseline)**:
  - **Version Bump Convention** (aligned with `cc-gateway`, `MAJOR.MINOR.PATCH`):
    - `PATCH` ranges **0–9**: when it reaches `9`, the next bump rolls over to `0` and increments `MINOR` (e.g. `1.0.9 → 1.1.0`, `1.5.9 → 1.6.0`).
    - `MINOR` ranges **0–19**: when it reaches `19`, the next bump rolls over to `0` and increments `MAJOR` (e.g. `1.19.9 → 2.0.0`).
    - Mobile native `buildCode` (Android `versionCode` / iOS `CURRENT_PROJECT_VERSION`) increments `+1` monotonically on each native shell version bump.
    - Pure-frontend OTA hot updates (`ota-*` / `mode=ota-only`) keep `X.Y.Z` unchanged and only advance `webBuild` (`YYYYMMDD.HHmmss-<hash>`).
    - Use `npm run version:bump` (`--patch` / `--minor` / `--major` / `--set=X.Y.Z` / `--dry-run`) to atomically synchronize `version-policy.json`, `package.json`, `package-lock.json`, `android/app/build.gradle`, and `ios/App/App.xcodeproj/project.pbxproj`.
  - `version-policy.json` is the single source of truth for decoupled `shells.{desktop, android, ios}` versions vs `minVersionForOta` / `minBuildCodeForOta` and `backend` `apiCapabilities` (enforced by unit tests against `package.json`, `android/app/build.gradle`, and `ios/App/App.xcodeproj/project.pbxproj`, including `PATCH 0–9` / `MINOR 0–19` bounds).
  - Before pushing a full release tag `vX.Y.Z`, ensure `package.json` and `version-policy.json` match `X.Y.Z` exactly (enforced by `.github/workflows/release.yml`). Never bump versions or push release tags autonomously unless the user explicitly asks; keep published GitHub Release notes bilingual (`中文 / English`).
  - Pushing to `main` runs `.github/workflows/ci.yml` only (never auto-publishes client updates). Push tag `ota-*` (or dispatch `release.yml` with `mode=ota-only`) for pure-frontend OTA hot updates; push tag `v*` (or `mode=full`) for full multi-platform installers + OTA.
  - Because Mobile/Web clients may switch dynamically between LAN and Cloud backend nodes running different versions, gate any post-`1.0.0` backend-dependent UI feature via `hasConnectedNodeCapability("<cap>")` (`src/web/services/ota-updater.ts`) while keeping `v1.0.0` baseline features backward-compatible.
- **Tiered E2E Skill (`/twinklebot-e2e`) & Feature-Sync / Release Gate Convention**:
  - Canonical reusable Agent Skill lives at `.agents/skills/twinklebot-e2e/SKILL.md` (symlinked into `.claude/skills` and `.pi/skills`, with slash entry points for OpenCode `.opencode/commands/twinklebot-e2e.md` and Pi `.pi/prompts/twinklebot-e2e.md`), backed by machine-readable `references/catalog.json` and `references/test-plan.md`.
  - **No trigger on small local preview edits**: Do **NOT** auto-trigger E2E test runs or interrupt the user when making small local tweaks, UI adjustments, or quick local previews. Only run E2E locally when the user explicitly asks (`/twinklebot-e2e ...`) or at the GitHub Release build boundary.
  - **GitHub Release / version build interactive E2E gate**: Whenever preparing a GitHub version build (running `version:bump` for release, pushing `v*` / `ota-*` tags, or dispatching `.github/workflows/release.yml`), automatically inspect impacted areas via `npm run e2e:sync-check -- --since-last-tag` and **actively ask the user** whether to run automated E2E tests and at which level (`affected+p0` **recommended default** = changed areas + P0 core; `all` = full 82-case suite; `p0+p1`; `p0`; `affected`; or `skip`). Both `scripts/run-e2e.mjs --tier=<level>` and `release.yml` (`e2e_level` input) support all 6 levels.
  - **Catalog sync on new features**: When adding brand-new user-facing features (new routes under `src/server/routes/`, new UI components under `src/web/components/`, new bot tools under `src/agent/bot-tools/`, or new `executor/executor.py` endpoints), keep `references/catalog.json`, `references/test-plan.md`, and `test/e2e/*.e2e.ts` in sync before committing (enable local non-blocking hooks via `npm run hooks:install`).
  - **Report locations**: Raw JSON/screenshots stay gitignored under `test-results/`; human-readable Markdown reports auto-generate to `test-results/reports/latest.md` (and timestamped `e2e-report-*.md`). Archive milestone reports to `docs/e2e-reports/` via `npm run e2e:report:archive`.
- **Product Issues Backlog (`docs/product-issues.md`)**: `docs/product-issues.md` is the single product issues / improvement backlog (`PI-XXX`, append-only, problem + exact `file:line` root cause only — never write fix proposals into it). Whenever fixing a tracked `PI-XXX` item, update its status column in `docs/product-issues.md` to `FIXED (<short-sha>)`.
- **Security**: Never commit or log `.env`, API keys, the executor token, or `data/`.
